# 版本号与发布规范（Phase 3 / B-09）

## 1. 版本号规则（2026-10-10 起）

- **单一事实来源**：`app/config.py` 的 `APP_VERSION` 与 **git tag 同名**（tag 形如 `V1.2.0`，带 `V` 前缀）。
  前端通过 `GET /api/v1/app-info` 动态读取 `APP_VERSION` 展示，因此"页面上看到的版本 = 代码里的版本 = tag"。
- 语义：`V主.次.修订`
  - **主**：不兼容的结构性变更（表结构大改、接口契约变更、调度架构调整）
  - **次**：向后兼容的功能新增（如本次企业级改造：可观测/鉴权/门禁/拆分）
  - **修订**：向后兼容的问题修复
- 历史遗留不追溯：`V1.1.6` 之前的 tag 与 `APP_VERSION` 不一致属已知历史问题，不再回填。

## 2. 发布步骤（与 G-10 脚本一致）

```powershell
# ① 确认工作区干净、测试通过
git status --porcelain
python -m pytest -m "not integration"
python -m ruff check .

# ② 改 APP_VERSION + 打 tag（tag 打在发布提交上）
#    例：APP_VERSION = "1.2.1" → git tag V1.2.1
git tag V1.2.1
git push AutoReplenishment main --tags

# ③ 发布（构建→按 commit SHA 打标→切换→冒烟；冒烟会核对容器内 APP_BUILD_SHA 与本次 commit）
powershell -ExecutionPolicy Bypass -File scripts\release.ps1

# ④ 出问题回滚（回到 _tmp\last_release.json 记录的上一个镜像标签）
powershell -ExecutionPolicy Bypass -File scripts\rollback.ps1
```

## 3. 制品标识的两个层级

| 标识 | 含义 | 位置 |
| --- | --- | --- |
| `APP_VERSION` / git tag | **业务版本**，人看（页面展示、变更记录） | `app/config.py`、git tag |
| `APP_BUILD_SHA` | **制品版本**，机器核对（镜像烧入的 commit SHA） | `api/Dockerfile` ARG → 容器 env；`release.ps1` 冒烟核对 |

## 4. 变更记录要求

- 每次发版在《整改方案.md》第 15 章「变更记录」追加一行（版本 / 日期 / 修改人 / 修改内容）；
- 涉及业务口径的变更必须写明"谁确认、口径是什么"（例：趋势系数上限 1.5 已于 2026-10-10 由业务确认保留）。
