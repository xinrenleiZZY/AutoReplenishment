# 数据治理（Phase 3 / B-07）

目的：让 `api_raw_responses` 与 `p_id/` 的增长**可预期、可归档、可审计**，同时避免"静默删数据"。

## 1. 保留期参数（可在「参数配置」页改，改动会进 G-12 审计）

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `raw_retention_days` | 90 | `api_raw_responses` 保留天数（早于 today-N 的行可归档/删除） |
| `p_id_retention_days` | 180 | `p_id` 抓取产物保留天数（`sales_history/*.json`、`sellable_gap/`、`sif_lifecycle/`） |

## 2. 查看体量（只读，随时可跑）

```powershell
# api_raw_responses 行数 / 最老与最新抓取日期 / 表占用
python scripts\purge_raw_responses.py
```

## 3. 归档 + 清理

```powershell
# ① 原始接口响应：先归档成 _archive/api_raw_responses_<cutoff>.jsonl.gz，再分批删除（批 2000 行）
python scripts\purge_raw_responses.py --days 90 --archive --yes

# ② p_id 抓取产物：移动到 _archive/p_id/<yyyyMMdd>/（移动而非删除，可恢复）
python scripts\archive_p_id.py --days 180 --yes
```

两个脚本**默认 dry-run**：不加 `--yes` 只打印"待处理清单 + 体积"，不会改动任何数据。

## 4. 设计取舍

- 不做"进程内静默自动清理"：数据删除属高风险动作，必须由人显式执行（`--yes`）并留痕；
- 归档先写盘、成功后再删库（`archive_and_purge` 按批写 gzip 后立即删除该批，避免整表驻留内存）；
- `p_id` 采用"移动归档"，`_archive/` 已加入 `.gitignore`，不污染仓库、不占版本库体积；
- 保留期参数走参数表 → 变更记录在 `config_audit_logs`（G-12），可追溯"谁把保留期从 90 改成 30"。
